## 1. 系统概述

### 1.1 系统定位

本系统为**健康饮食积分管理系统**，面向中老年用户提供饮食建议工具，通过微信小程序作为前端触点，结合AI视觉识别与文本生成能力，实现"拍照打卡→AI分析→健康报告→到店服务"的完整闭环。

系统核心目标：

- 帮助中老年用户建立健康饮食习惯
- 通过积分体系激励用户持续参与
- 以AI报告为危机钩子引导到店转化
- 构建代理商→服务商→用户的商业闭环

### 1.2 核心商业闭环

```
线上评估 → AI报告 → 危机钩子引导到店 → 代理商线下讲解 → 会员转化
    ↑                                                        ↓
    ← 每日打卡/课程 → 积分获取 → 积分消费 → 拉新 ←──────────┘
```

闭环拆解：

| 阶段 | 触发点 | 关键动作 | 系统支撑 |
|------|--------|----------|----------|
| 线上评估 | 用户首次进入/月度复评 | 填写健康问卷（8类50+题） | questionnaire + questionnaire_answers |
| AI报告 | 问卷提交 | 生成危机钩子报告（简版）+ 7天调理方案（完整版） | reportGenerator + SiliconFlow Qwen3-VL |
| 危机钩子 | 报告展示 | 提示"专属方案已生成，到店领取" | report.crisis_hook + 服务网点信息 |
| 代理商线下 | 到店 | 专业解读报告、讲解方案 | agent + service_provider_reception |
| 会员转化 | 线下讲解 | 升级为会员（identity_type: member） | agent/convert-to-member |
| 每日打卡 | 每日 | 图标打卡/图片打卡（AI识别） | clock_in_records + aiRecognition |
| 课程学习 | 每日 | 观看健康课程 | course_records |
| 积分获取 | 打卡/签到/课程/拉新 | 积分发放 | points_history + configCache |
| 积分消费 | 兑换礼品/核销 | 积分扣减 | points_write_off + gift_exchanges |
| 拉新 | 分享码邀请 | 新用户注册绑定 | share_code + referrer_id |

### 1.3 用户角色体系

| 角色 | role值 | identity_type | 说明 |
|------|--------|---------------|------|
| 游客 | user | guest | 未完成问卷的访问者 |
| 普通用户 | user | user | 已完成问卷的注册用户 |
| 会员 | user | member | 经代理商转化，享有完整报告查看等权益 |
| 代理商 | agent | agent | 负责用户转化、积分核销、发布信息 |
| 服务商 | service_provider | service_provider | 提供线下服务、接待用户 |
| 管理员 | admin | admin | 后台管理（配置/违禁词/Prompt/报表等） |
| 超级管理员 | admin (is_super=true) | admin | 最高权限：管理admin账号、重置密码 |

## 5. 权限体系

### 5.1 中间件链

```
请求 → authMiddleware → roleCheck/agentOnly/adminOnly/... → 业务Handler → 响应
```

### 5.2 中间件详细说明

| 中间件 | 函数 | 校验逻辑 | 应用场景 |
|--------|------|----------|----------|
| **authMiddleware** | `authMiddleware(req,res,next)` | 从Authorization头提取Bearer Token，jwt.verify显式指定HS256算法，检查Token黑名单 | 所有 `/api/*` 路由（除auth/health） |
| **roleCheck** | `roleCheck(...allowedRoles)` | 检查 `req.user.role` 是否在允许角色列表中 | 通用角色校验工厂 |
| **adminOnly** | `adminOnly` | `roleCheck('admin')` | `/api/admin/*` |
| **superAdminOnly** | `superAdminOnly` | role=admin 且 DB查询 `is_super=true` | 创建/修改admin账号、重置密码等关键操作 |
| **agentOnly** | `agentOnly` | `roleCheck('agent', 'admin')` | `/api/agent/*` |
| **serviceProviderOnly** | `serviceProviderOnly` | `roleCheck('service_provider', 'admin')` | `/api/service-provider/*` |
| **userOnly** | `userOnly` | `roleCheck('user', 'admin')` | 纯C端用户专属活动（不强制应用到 /api/user/*） |

**设计要点：**

- admin角色始终拥有所有权限（穿透所有roleCheck）
- `/api/user/*` 仅使用 `authMiddleware` 保护（任何已登录角色均可访问），因为代理商/服务商/管理员本身也是用户，需要访问自己的积分、报告等
- `superAdminOnly` 需额外查库获取 `is_super` 字段（JWT payload不含此字段，避免泄露）

### 5.3 JWT Token结构

```json
{
  "id": "uuid",                    // 用户ID
  "openid": "wx_openid",          // 微信openid（仅Token内，不返回客户端）
  "role": "user|agent|service_provider|admin",
  "identity_type": "guest|user|member|service_provider|agent",
  "agent_id": "uuid|null",        // 关联代理商ID
  "service_provider_id": "uuid|null", // 关联服务商ID
  "jti": "random-uuid",           // Token唯一标识（用于黑名单）
  "iat": 1700000000,              // 签发时间
  "exp": 1700604800               // 过期时间（7天）
}
```

**签名算法：** HS256（显式指定，防算法混淆攻击）
**有效期：** 7天（可配置 `JWT_EXPIRES_IN`）
**黑名单：** 登出时将jti写入内存Map，定期清理过期项

## 6. 安全机制

### 6.1 认证与加密

| 安全项 | 实现方式 | 详细说明 |
|--------|----------|----------|
| **JWT防算法混淆** | `jwt.verify(token, secret, { algorithms: ['HS256'] })` | 显式指定HS256算法，防止攻击者将alg改为none或RS256→HS256绕过签名验证 |
| **手机号加密** | AES-256-GCM + PBKDF2密钥派生 | PBKDF2(SHA256, 100000次迭代, 32字节密钥)；每次IV随机保证语义安全；authTag提供完整性校验防篡改 |
| **密码哈希** | bcrypt (saltRounds=10) | Web后台密码存储，强度8-32位且至少含字母和数字 |
| **登录响应脱敏** | 移除openid字段 | 登录接口响应不返回openid，防止通过接口泄露微信openid |
| **Token黑名单** | jti + 过期时间Map | 登出时写入黑名单，每小时清理过期项，防止已登出Token被重放 |

### 6.2 权限与访问控制

| 安全项 | 实现方式 | 详细说明 |
|--------|----------|----------|
| **superAdminOnly** | role=admin + DB查is_super | 保护关键操作（创建admin/重置密码/修改权限），JWT不含is_super需额外查库 |
| **参数白名单校验** | express-validator | 所有入参按白名单校验类型/范围，拒绝未定义字段 |
| **行锁防竞态** | Sequelize事务 + SELECT FOR UPDATE | 积分变动、库存扣减等并发操作使用行锁，防止超扣/超兑 |

### 6.3 输入与内容安全

| 安全项 | 实现方式 | 详细说明 |
|--------|----------|----------|
| **违禁词ReDoS防护** | 正则安全编译 + 超时兜底 | 违禁词pattern编译失败不阻塞；单条正则限制匹配长度防止回溯爆炸 |
| **SQL LIKE转义** | `%` → `\%`，`_` → `\_` | 搜索接口转义LIKE通配符，防止用户输入构造全表扫描 |
| **幂等键** | 请求幂等键去重 | 关键操作（积分发放/核销）携带幂等键，防重复提交 |
| **内容安全fail-safe** | 服务不可用→拒绝不放行 | 图片/文本安全检测服务未配置或调用失败时返回pass=false，不降级放行 |
| **医疗红线** | 上下文感知正则 + 自动重试 | 报告生成后校验医疗红线，命中则自动重试一次，仍命中则flagged=true进人工审核 |
| **违禁词双层** | 硬编码基线 + DB动态规则 | 硬编码规则不可删除（合规基线），DB规则可运营维护，并集生效 |

### 6.4 传输与存储安全

| 安全项 | 实现方式 | 详细说明 |
|--------|----------|----------|
| **HTTPS强制重定向** | Express中间件 + Nginx 301 | 生产环境通过X-Forwarded-Proto判断，HTTP→HTTPS |
| **CORS白名单** | 环境变量ALLOWED_ORIGINS | 生产环境仅允许配置的来源，开发环境允许* |
| **Cross-Origin-Resource-Policy** | 静态资源设cross-origin | 解决helmet默认same-origin导致小程序image标签跨域拦截 |
| **OSS孤儿清理** | 关联删除时同步删除OSS文件 | 用户/报告删除时清理关联的OSS对象，避免存储泄漏 |
| **请求体限制** | JSON 10MB + Nginx 10MB | 防止大文件上传DoS |
| **Helmet安全头** | helmet() | X-Frame-Options:DENY, X-Content-Type-Options:nosniff, HSTS等 |

## 7. 业务时区

### 7.1 设计原则

业务时区统一为 **Asia/Shanghai (UTC+8)**，不依赖服务器本地时区，确保部署在任意时区的云服务器上，"今日0点"/"满N天"/"本月1号"等日历边界均与北京用户感知一致。

### 7.2 多层时区保障

| 层级 | 配置 | 说明 |
|------|------|------|
| 环境变量 | `TZ=Asia/Shanghai` | app.js启动时检查，未设置则强制设为Asia/Shanghai |
| Sequelize | `timezone: '+08:00'` | JS Date→DB DATETIME写入时的格式化时区 |
| MySQL会话 | `dialectOptions.timezone: '+08:00'` | 连接后执行SET time_zone='+08:00'，确保NOW()/CURDATE()等函数返回北京时间 |
| node-schedule | 指定tz选项 | 定时Job按北京时区触发，避免UTC偏移 |
| 日期工具 | UTC数学运算 | `utils/date.js`通过UTC偏移计算北京0点，不依赖服务器local time |

### 7.3 关键时区函数（utils/date.js）

| 函数 | 说明 | 实现 |
|------|------|------|
| `getBusinessDayStart(date)` | 获取北京时区今日0点（UTC Date） | 北京时间 = UTC+8h，取年月日，构造UTC 0点再减8h |
| `getBusinessDaysAgo(days, date)` | N天前北京0点 | todayStart - N×86400000 |
| `getTodayString()` | 今日YYYY-MM-DD（北京时区） | formatBusinessDate(new Date()) |
| `isSameBusinessMonth(a, b)` | 判断同月（北京时区） | 比较UTC+8h后的年月 |
| `getBusinessMonthStart(date)` | 本月1号0点（北京时区） | UTC偏移构造 |
| `getNextBusinessMonthStart(date)` | 下月1号0点（北京时区） | 用于月度次数重置 |
